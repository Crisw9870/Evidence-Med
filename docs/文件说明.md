这些 JSON 文件组成了一条“原始医疗问答 → 强教师蒸馏 → 证据校验 → SFT 训练数据”的流水线。并不是所有文件都会拿去训练。

整体关系是：

```text
medical_100k.jsonl
        ↓ 病例筛选、去重、预划分
00_candidates.jsonl
        ↓ 发送给强教师
01_teacher_raw.jsonl
        ↓ 原文证据硬校验
03_validated_full.jsonl
        ↓ 转换为训练器支持的 ShareGPT 格式
train.jsonl / validation.jsonl / test.jsonl
```

## 1. `00_candidates.jsonl`

位置：

[00_candidates.jsonl](/home/medgpt/data/evidence_sft/00_candidates.jsonl)

作用：保存准备交给强教师重构的病例。

每条大致是：

```json
{
  "source_id": "medical_xxx",
  "split": "train",
  "category": "内科",
  "task_type_hint": "diagnostic_reasoning",
  "case_text": "患者最近反复胸痛……",
  "original_answer": "原数据里的旧回答",
  "candidate_score": 8
}
```

字段含义：

- `source_id`：稳定样本编号，用于去重和断点续跑；
- `split`：提前决定属于训练、验证还是测试；
- `category`：病例科室；
- `task_type_hint`：规则初步判断是诊断推理还是确诊后管理；
- `case_text`：患者病例原文；
- `original_answer`：旧数据中的低质量回答，给教师作参考；
- `candidate_score`：病例信息丰富度评分。

为什么要提前写这个文件：

- 避免把 10 万条数据全部发送给教师；
- 保证同一批实验可以重复；
- 训练集和测试集在教师生成前就分开；
- 教师调用中断后可以按 `source_id` 继续。

它不是最终训练文件。

## 2. `00_candidates.stats.json`

位置：

[00_candidates.stats.json](/home/medgpt/data/evidence_sft/00_candidates.stats.json)

作用：记录候选筛选统计，例如：

```json
{
  "input_rows": 100000,
  "unique_case_candidates": 59095,
  "selected": 200,
  "task_counts": {
    "diagnostic_reasoning": 120,
    "confirmed_management": 80
  },
  "split_counts": {
    "train": 153,
    "validation": 24,
    "test": 23
  }
}
```

这个文件用于：

- 检查数据比例是否合理；
- 写项目 README 和实验报告；
- 面试时说明筛选过程；
- 发现某个科室过多或任务分布失衡。

它也不参与训练。

## 3. `01_teacher_requests.preview.jsonl`

位置：

[01_teacher_requests.preview.jsonl](/home/medgpt/data/evidence_sft/01_teacher_requests.preview.jsonl)

作用：展示将要发送给强教师的完整请求，但不真正调用 API。

每条包含：

```json
{
  "source_id": "medical_xxx",
  "model": "教师模型名",
  "messages": [
    {"role": "system", "content": "证据蒸馏规则……"},
    {"role": "user", "content": "病例原文和旧回答……"}
  ]
}
```

它主要用来人工检查：

- Prompt 是否正确；
- 是否意外使用指南；
- 病例原文是否完整；
- 是否把旧回答明确标成了“低质量参考”；
- 是否要求 evidence 必须逐字来自病例。

它相当于 API 请求的预览文件，不参与训练，也不会自动发送。

## 4. `01_teacher_raw.jsonl`

位置：

[01_teacher_raw.jsonl](/home/medgpt/data/evidence_sft/01_teacher_raw.jsonl)

作用：保存强教师成功返回的原始蒸馏结果。

一条记录大致是：

```json
{
  "source_id": "medical_xxx",
  "case_text": "患者病例原文",
  "original_answer": "旧回答",
  "teacher_model": "教师模型",
  "prompt_version": "evidence-sft-v1",
  "status": "ok",
  "teacher_text": "教师原始输出",
  "parsed_output": {
    "task_type": "diagnostic_reasoning",
    "evidence_sufficiency": "insufficient",
    "evidence": [
      {
        "id": "E1",
        "span": "反复胸痛2周",
        "role": "需要排查心血管问题"
      }
    ],
    "critical_evidence_ids": ["E1"],
    "missing_information": ["心肌标志物等检查"],
    "clinical_reasoning": "……",
    "final_answer": "……"
  }
}
```

这是最重要的中间产物，因为它保留了：

- 教师看到的原始病例；
- 原始旧回答；
- 教师原始文本；
- 解析后的结构化结果；
- 教师模型、Prompt 版本和生成时间；
- 是否发生重试或截断。

为什么不能直接用它训练：

教师虽然按要求生成了 evidence，但还没有证明 evidence 确实来自病例原文，需要再经过校验。

另外它包含病例、旧回答和完整教师记录，体积较大，通常不适合直接公开。

## 5. `01_teacher_failed.jsonl`

位置：

[01_teacher_failed.jsonl](/home/medgpt/data/evidence_sft/01_teacher_failed.jsonl)

作用：记录教师调用或格式解析失败的响应。

常见状态：

```json
{
  "source_id": "medical_xxx",
  "status": "parse_error",
  "finish_reason": "length",
  "error": "empty_teacher_content"
}
```

失败原因可能是：

- 返回为空；
- 教师输出被截断；
- JSON 缺少右括号；
- API 超时；
- 达到最大输出 token；
- 返回了自然语言而不是 JSON。

这个文件不参与训练。

注意，一个 `source_id` 可能同时出现在：

- `01_teacher_failed.jsonl`
- `01_teacher_raw.jsonl`

这表示它第一次失败，后来重试成功，并不冲突。判断最终是否成功，应当以 `01_teacher_raw.jsonl` 中是否存在该 ID 为准。

## 6. `03_validated_full.jsonl`

位置目前可能在：

- [烟测校验结果](/home/medgpt/data/evidence_sft/smoke/03_validated_full.jsonl)
- [增量校验结果](/home/medgpt/data/evidence_sft/incremental/03_validated_full.jsonl)

作用：保存通过证据硬校验的教师样本。

校验器会检查：

- JSON 字段是否完整；
- `task_type` 是否合法；
- `evidence_sufficiency` 是否合法；
- 每个 `evidence.span` 是否逐字存在于 `case_text`；
- evidence ID 是否重复；
- `critical_evidence_ids` 是否真实存在；
- 判断和最终回答是否过短；
- 教师是否生成了病例中没有的数字。

校验后 evidence 会增加位置：

```json
{
  "id": "E1",
  "span": "反复胸痛2周",
  "start": 7,
  "end": 14
}
```

`start/end` 可以证明该证据确实能定位回病例原文，这就是项目中的“原文证据绑定”。

这个文件适合：

- 数据审计；
- 错误分析；
- 人工抽检；
- 构造后续 masked 样本。

但它仍然不是直接送进当前 SFT Trainer 的文件。

## 7. `03_rejected.jsonl`

作用：保存教师返回了内容，但没有通过证据硬校验的样本。

例如：

```json
{
  "source_id": "medical_xxx",
  "validation_errors": [
    "evidence_span_not_in_case"
  ]
}
```

常见拒绝原因：

- 教师把证据改写了，不是原文连续子串；
- 教师声称证据充分，却没有给 evidence；
- 关键证据 ID 不存在；
- 最终回答为空；
- 输出结构缺少字段。

这些样本不会进入训练集。

这个文件很适合用于项目的失败案例分析。

## 8. `03_validation.stats.json`

作用：记录教师数据的最终验收统计：

```json
{
  "counts": {
    "total": 200,
    "accepted": 185,
    "rejected": 15
  },
  "split_counts": {
    "train": 145,
    "validation": 20,
    "test": 20
  },
  "warning_counts": {
    "generated_numbers_require_review": 30,
    "task_type_changed_by_teacher": 15
  }
}
```

这里区分两类问题：

- `error`：硬错误，样本不能训练；
- `warning`：样本通过，但建议人工抽检。

例如教师回答中出现“复查 3 个月”：

- “3个月”未必是患者事实，可能是一般医学建议；
- 所以不能简单判错；
- 校验器会标记为 `generated_numbers_require_review`。

## 9. `train.jsonl`

这是最终真正用于 Evidence-SFT 训练的文件。

格式兼容仓库现有的 `supervised_finetuning.py`：

```json
{
  "source_id": "medical_xxx",
  "split": "train",
  "task_type": "diagnostic_reasoning",
  "masked": false,
  "conversations": [
    {
      "from": "human",
      "value": "以下是患者提供的病例描述……病例描述：患者反复胸痛……"
    },
    {
      "from": "gpt",
      "value": "{\"evidence\":[...],\"clinical_reasoning\":\"...\",\"final_answer\":\"...\"}"
    }
  ]
}
```

学生模型训练时只看到：

```text
病例描述 → 教师构造的证据、医学判断和最终回答
```

学生不会看到 `original_answer`。旧回答只用于教师生成阶段。

`masked: false` 表示这是完整病例证据样本。后续构造关键证据遮蔽数据时，才会出现：

```json
"masked": true
```

## 10. `validation.jsonl`

用于训练过程中：

- 计算 validation loss；
- 选择 checkpoint；
- 观察模型是否过拟合；
- 调试格式学习效果。

它不能和 `train.jsonl` 重复。

## 11. `test.jsonl`

只用于 Evidence-SFT 完成后的最终测试，例如：

- evidence 原文命中率；
- JSON 格式正确率；
- 证据充分性判断；
- 最终回答质量。

不能用它调整 Prompt、训练参数或者筛选 checkpoint，否则测试集会被污染。

## 12. `smoke/` 和 `incremental/`

这两个是临时质检目录。

### `smoke/`

仅用于最初 3 条真实 API 调用：

```text
smoke/
├── 03_validated_full.jsonl
├── 03_rejected.jsonl
├── train.jsonl
├── validation.jsonl
├── test.jsonl
└── 03_validation.stats.json
```

它的意义是验证整条链路能跑通，不是正式数据集。

### `incremental/`

教师批量生成尚未结束时，对当前已生成部分做提前校验。

用于确认：

- evidence 规则是否工作；
- 教师质量是否稳定；
- 是否应该停止批量调用、调整 Prompt。

最终批次完成后，会在正式目录重新全量校验；`smoke/` 和 `incremental/` 都不会作为最终训练输入。

## 最终你真正需要关注的文件

如果从不同角色看：

| 角色 | 需要关注 |
|---|---|
| 教师生成阶段 | `00_candidates.jsonl` |
| 数据审计 | `01_teacher_raw.jsonl` |
| 失败分析 | `01_teacher_failed.jsonl`、`03_rejected.jsonl` |
| 人工抽检 | `03_validated_full.jsonl` |
| SFT 训练 | `train.jsonl` |
| 训练监控 | `validation.jsonl` |
| 最终评测 | `test.jsonl` |
| README/简历数据 | 各种 `*.stats.json` |

最核心的理解是：

> `01_teacher_raw.jsonl` 是教师生成档案，`03_validated_full.jsonl` 是通过证据审计的数据，`train.jsonl` 才是最终喂给学生模型的 SFT 数据。
